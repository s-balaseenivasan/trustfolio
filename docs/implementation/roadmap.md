## Phase gates and open decisions

The user authorized Phase 1 as **draft engine only**. `D-03` confirms proposed group names and mandatory no-self-approval, fail-closed and no-admin-bypass controls. Actual approver assignments, monetary thresholds, delegation authorization and policy activation remain unresolved. `D-01` jurisdiction/currency/fiscal year/accounting basis and `D-02` fund policy must be resolved before final finance schema/posting contracts. `D-04` provider/recurring/refund behavior remains unresolved. `D-05` is resolved for club/volunteer existing-account adult-consent onboarding; donor/guest onboarding remains open. The Phase 6 intake slice uses INR paise and existing `PORTAL_USER` accounts as a conservative implementation boundary only; it does not settle the trust's final donor or currency policy. `D-06` disclosure policy must be resolved before public financial release.

For every phase: approve scope and migration design → back up/prepare rollback → implement behind a controlled release gate → run listed cases and existing regression suite → fix defects → record actual results and data migration evidence → stop for next approval. A skipped or blocked critical case prevents production enablement.

## Phase design packets

### Phase 0 — existing application audit

Read-only services/DB inventory: compare deployed migrations with schema, enumerate real and demo rows, inspect published documents lacking files, verification records with inaccessible sources, private file routes, current role grants and cache dependencies. No UI/schema change. Acceptance: findings have record counts and privacy-safe evidence; production backup capability is known. Tests: baseline public/admin browser checks and media/evidence queries. Risk: static repository review cannot prove production state.

### Phase 1 — foundation

Implemented locally: additive `AccessGroup`, `Permission`, mappings, draft `AccessGroupMembership`, `ApprovalPolicy/Instance/Decision`, draft delegation, `AuditEvent` and notification outbox; preserved legacy `User.role`. Services include scoped permission lookup, draft policy creation/simulation, versioning, and closed-gate approval transitions. UI is the ADMIN-only draft configuration, history and simulation page at `/admin/approvals`. Database migration includes proposed group catalog entries only and append-only history guards. No active membership, delegation or approval policy was created. Existing publication behavior remains unchanged by user direction. Acceptance executed for this **draft-only slice** is recorded in `../testing/test.md`; live transition/concurrency, notification delivery, broader multi-role portals and safeguard fixes are outside this authorization and remain pending. A future live activation plan must resolve remaining `D-03`, bind approvals to immutable target payloads, define return/cancellation/delegation/escalation rules, and prove full `T-APR-*` under concurrent database tests.

### Phase 2 — clubs

DB: `Club`, `ClubMembership`, invitation/decision history and club document links. Services: code generation, membership transitions, coordinator scope. UI: admin clubs and club portal/membership queue. Rules: historical suspension, unique active membership, no implicit project access. Acceptance/tests: `T-CLB-01` plus direct route/action permission checks. Rollback by disabling new portals; no hard delete.

Phase 2 design packet (2026-10-25): use an additive `Club` record with immutable generated code, bilingual draft profile, operational status and separate publication status. `ClubMembership` links existing `User` and `Club` and preserves status/role, with an append-only membership event trail. A coordinator grant must be explicitly scoped to one club and checked server-side on every read/action; membership alone never grants project access. A portal-only account role is needed before coordinator sign-in because the current `EDITOR` role grants unrelated content editing. No existing user is reclassified or given a new grant by migration. Club documents reference existing `Media` under private access, with deletion restricted while referenced. Club activity and contribution views derive from recorded membership/events; project contribution remains unavailable until Phase 4 assignments exist.

Services/API: transactional club create/update/suspend/archive and code generation; membership invitation/request/review transitions only after the onboarding authority and consent policy is resolved; scoped club read/write services and audit events. Server Actions recheck actor and target scope, validate all form input and return safe errors. UI: ADMIN club list, profile editor, membership queue and documents; `/club` dashboard and a club detail for authorized coordinators, with empty and suspended states. No public club page is released until a publication/disclosure review is approved.

Acceptance: one user may have memberships in several clubs; a coordinator for Club A receives no Club B private record through direct URL or action; suspended/archived clubs retain history and cannot accept new membership/work; duplicate active membership and stale transitions fail atomically; portal-only users cannot access `/admin`; existing public/admin routes still work. Run isolated PostgreSQL constraints/transaction tests, direct authorization checks and headed Chrome for ADMIN and club accounts. Rollback disables new routes/actions while retaining rows and audit history; enum additions and historical records are not destructively removed.

Phase 2 decisions confirmed by the user: membership requests and invitations target **existing accounts only**; applicants explicitly attest they are adults and consent to the named account-data use; a trust admin approves membership; a coordinator must already have approved active membership. The Phase 2 implementation adds an isolated `PORTAL_USER` account role, generated club code, bilingual draft profiles, operational status, membership invitation/request/review, immutable history, single coordinator appointment, private document upload/read, admin club screens and `/club` coordinator workspace. Self-approval is blocked. The existing publication path is unchanged; clubs are not yet public. In-app invitation and decision state is visible in the portal and notification outbox, while external delivery remains a later notifications phase. Age is self-attested, not independently verified; the trust admin is the checker. Project assignments, service hours and contribution performance depend on Phases 3–4.

Phase 2 acceptance evidence is in `../testing/test.md`. The local migration `20261025010000_phase2_clubs` was applied additively after isolated schema checks. Rollback keeps historical rows and disables `/club` and `/admin/clubs`; no destructive reversal is planned. If the trust later changes age/consent or coordinator multiplicity policy, a reviewed data migration and fresh consent may be required.

### Phase 3 — volunteers

Phase 3 decisions confirmed by the user: existing accounts only; adults self-attest and explicitly consent; trust admin approves attendance and service hours; reviewed logs are prepared for later certificate issuance, with no certificate output or signing authority selected. Existing Phase 2 club membership requests remain the admission workflow. New private `VolunteerProfile`, `VolunteerAvailability`, `VolunteerAttendance`, `VolunteerServiceLog` and append-only review histories are additive. The `/volunteer` portal lets a signed-in account create/edit their own profile and availability, submit attendance for approved active club membership, then submit hours for approved attendance. `/admin/volunteers` supports private search and trust-admin review/correction. Opted-in skills are visible to a coordinator only for an approved member of that coordinator's active club. No volunteer record enters public routes. Direct server actions enforce ownership, scope, no self-review and optimistic version checks; approved-only minutes are calculated from approved logs and attendance. Exact active duplicate activity claims are blocked by an index. Tests and limitations are recorded in `../testing/test.md`.

Project/task attribution, certificates, external notifications, independently verified age, full Tamil portal copy and public volunteer opportunity publication remain later work. The local additive migration `20261026054227_phase3_volunteers` was tested in a disposable schema before local application. Rollback disables `/volunteer` and `/admin/volunteers` while retaining consent, reviewed records and immutable history; schema/table drops are not part of rollback.

### Phase 4 — projects and tasks

DB: additive `Project` operational fields, assignment, milestone, task and task assignment. Services: assignment grants, task transition/dependency, progress/completion. UI: existing project editor linked to operational workspace plus club/volunteer task views. Rules: no duplicate Project; publication independent of operations. Acceptance/tests: `T-CLB-02`, `T-PRJ-01`, `T-TSK-01`, `T-REG-01`.

Phase 4 decisions confirmed by the user: only a legacy trust `ADMIN` may grant or change project-club assignments and select their coordinator; only a trust admin may review volunteer task completion; budget data in this phase is a planning note without monetary amounts or posting. Design the operational state, owner/manager and schedule on the **existing** `Project` row, with defaults that do not infer status from existing published content. Add a unique project-club assignment with active membership checks, scoped view/report permissions and append-only assignment/activity history. Tasks and milestones link the existing project; task assignments require an approved club member and current volunteer profile. A volunteer may update only a task assigned to them under an active project-club assignment. Task dependencies are internal to the same project and cycle checked; completion requires submission and independent admin review. Operational notes and task evidence remain private. Existing project publication, slug, public dates, translations and cache path stay unchanged. This packet authorizes no finance budget amount, campaign or public completion report.

### Phase 5 — fundraising

DB: request/campaign and evidence references. Services: request approval and separate publication eligibility. UI: admin request queue, campaign editor and public bilingual campaign preview. Rules: approved request alone never activates campaign. Acceptance/tests: `T-FND-01`, `T-I18N-01`, evidence/privacy regression.

Phase 5 decisions confirmed on 2026-10-26: draft request targets use INR stored as integer paise; only legacy trust `ADMIN` may create/edit drafts; at most one campaign is linked to one request; and campaign preparation remains private. Preserve Phase 1's hard live-approval gate and all existing project publication controls. Add private donation-request drafts under the existing project, with versioned edit history, private supporting evidence and an explicit submission boundary. A linked campaign draft is planning material only, even while its request is still a draft; it is not an approved or publicly active campaign. Request submission, approval, campaign release and collection remain closed until actual approver assignments, threshold policies and public-release rules are approved and activated. Use existing admin and private-media patterns; do not add a second Project or route fundraising drafts through existing public DTOs. Tests cover exact paise parsing, draft edits, stale versions, one-to-one cardinality, evidence privacy, denied submission/publication and public regression. Migration is additive; rollback disables new routes/actions and retains request/evidence history.

### Phase 6 — donations

UI: donor portal, checkout and finance manual-collection queue. Rules: pending/failed/unverified excluded from confirmed totals. Acceptance/tests: `T-DON-*`, `T-PUB-01`, provider sandbox settlement and direct permission checks. **Feature flag remains off for real collection until Phase 7 posting contract is approved and tested.**

### Phase 7 — finance

DB: funds, ledger accounts, fiscal periods, budgets/lines, expenses/payments, journals/lines with unique source and immutability controls. Services: posting, reversal, availability/commitment, period and expense state machines. UI: finance workbench, fund/budget/expense and journal review. Rules: accountant-approved policy, balanced atomic posting and restrictions. Acceptance/tests: `T-FIN-01..03` and accountant reconciliation of sample cases. Implement posting foundation early enough to unblock Phase 6 live activation.

### Phase 8 — reporting

DB: reconciliation imports/lines/matches and approved public report snapshots. Services: settlement matching, statement queries, exports and disclosure review. UI: reconciliation queue, internal reports, public utilization pages. Rules: report tie-outs and no raw private data. Acceptance/tests: `T-FIN-04`, `T-PUB-01`, `T-I18N-01`.

### Phase 9 — production readiness

Services/UI: hardening, monitoring, backup/restore, incident runbooks, performance tuning and browser fixes. DB: reviewed indexes/retention, no unapproved destructive change. Acceptance/tests: all critical cases pass, independent portal and Chrome headed coverage, restore rehearsal, provider certification and public regression. Record residual risks and named operational owners.

## Phase 6 gated-slice record

Additive migration `20261026073000_phase6_donation_intake` adds `DonorProfile`, `Donation`, `DonationHistory` and `DonationEvidence`; `20261026073100_phase6_foreign_key_names` aligns constraint names. It links donor profiles only to existing `PORTAL_USER` accounts, uses anonymous-by-default display, stores pending offline intake in exact INR paise and requires a published, non-demo project. DB constraints reject non-positive/other-currency amounts, any state other than `PENDING_VERIFICATION`, duplicate intake keys, referenced account/media deletion and edits to donation history. ADMIN-only `/admin/donations` links an account and records cash/bank/UPI intake; evidence uses `private/donation-evidence/` with ADMIN-only upload/read. `/donor` requires a current signed-in account and donor profile, and returns only that account's pending records. Existing public campaign/project DTOs do not include donor or intake information.

`src/server/payments/provider.ts` defines the provider contract and a test-only HMAC mock; the production provider resolver always fails closed. This is not a live/sandbox checkout endpoint and no provider SDK or credentials are configured. No donation verification, allocation, receipt, refund, recurring mandate, payment webhook persistence, financial posting or public collection total exists in this slice. These remain blocked by D-01/D-03/D-04 and Phase 7 accounting/posting approval. Existing-account/INR-only choices are current implementation boundaries, not final policy approvals. Isolated migration and unit/headed results passed; both additive migrations have been applied to the local development database only, with no backfill. See `../testing/test.md`. Rollback disables donor/intake routes and retains private records/evidence; no destructive down migration is planned.

## Rollback and data policy

For additive migrations, maintain application compatibility for one deploy window, validate backfills before constraints, and take a restorable backup. Do not delete existing data or reset the database. Feature rollback disables new routes/collection; financial rows already posted remain and are corrected only through approved reversal. Never convert demo impact figures into finance opening balances. For a schema removal or data transformation, submit a separate destructive migration plan and request explicit approval.
