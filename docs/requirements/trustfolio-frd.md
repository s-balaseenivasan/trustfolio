# Trustfolio functional requirements (FRD)

Status: **requirements baseline; Phase 1 draft approval and Phase 2–5 operational subsets implemented locally**. Updated: 2026-10-26. The table describes full outcomes, so partial phase work is identified explicitly and does not imply live financial approval or campaign publication. `D-*` refers to decisions in `../architecture/trustfolio-expansion.md`.

## Product outcome and actors

Trustfolio must connect club formation, volunteer participation, execution of the existing `Project`, fundraising, verified collection, restricted allocation, authorized spending, balanced accounting, reporting, and safe public evidence. Actors: trust administrator, content editor, club coordinator, volunteer, donor, finance maker, finance checker, accountant/poster, reconciler, public visitor, and payment provider. One person may hold several roles; each action still requires its own permission and resource scope.

The existing public site and content dashboard must remain functional and bilingual. Existing demo rows are fictional and must never become opening financial balances or official claims.

## Business flows and state rules

1. **Club work:** create club → invite/approve membership → assign club to existing project → authorize scoped tasks → review work/attendance → report contribution. Suspension blocks new activity and keeps historical assignment records.
2. **Fundraising:** project request draft and optional linked private campaign planning draft → request submitted → returned/rejected/approved under a policy snapshot → campaign release review → public active → closed. The confirmed limit is one campaign per request. A planning draft has no approval, public visibility or donation collection effect.
3. **Online donation:** designed flow is pending order → provider-verified paid event → confirmed donation → fund allocation and balanced journal → receipt → settlement reconciliation. Phase 6 currently has no checkout/webhook endpoint; live flow is closed until provider and posting approval.
4. **Manual donation:** current flow ends at ADMIN-recorded private pending intake with private evidence. Checker verification, reconciliation, confirmation, posting and receipt are blocked until their policy and ledger gates are active. The maker cannot approve or verify their own entry.
5. **Expense:** request → budget/fund validation → approval → payment authorization → executed payment → journal → reconciliation. Approval does not itself mean payment.
6. **Public transparency:** posted/verified data → disclosure calculation → authorized review → publication snapshot → cache invalidation. Withdrawals preserve an audit trail.

## Explicit exclusions until decided

No tax-deductibility claim, statutory receipt format, recurring mandate guarantee, cross-currency conversion, minor volunteer workflow, automatic fund transfer, or transaction-level public release is assumed. These require `D-01` to `D-06` or a later approved change request.

## Acceptance and handoff

Each phase must demonstrate its `FR-*` items against the `T-*` scenarios in the test plan, record passed/failed/skipped/blocked evidence, and show that existing public and admin behavior still works. A document entry is a proposed requirement, never evidence of implementation.
